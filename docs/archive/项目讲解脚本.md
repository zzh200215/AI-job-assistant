## 第一段：开场 & 项目背景（2-3 分钟）

### 🎬 画面：首页 + 系统概览

**台词：**
> 大家好，今天我来演示我的毕业设计——《基于 Agentic RAG 与多智能体协作的智能招聘与职业规划平台》。

> 简单来说，这是一个 AI 求职助手。但它不是那种你问一句它答一句的普通 AI 聊天工具。它做了三件不一样的事：

> **第一**，它用 Agentic RAG 替代了普通 RAG。不是简单检索一段文本就生成答案，而是先规划需要什么知识、多次检索、交叉验证，最后才生成结果。

> **第二**，它用多个 AI 智能体替代了单一大模型。6 个 Agent 各司其职——一个专门看简历、一个专门分析岗位、一个专门做匹配、一个专门出面试题、一个专门做规划、一个专门汇总报告——就像一个完整的招聘顾问团队。

> **第三**，它不是纯 LLM 驱动。我做了规则引擎 + LLM 的混合架构，评分靠规则、解释靠 LLM，输出比纯 AI 稳定得多。

**画面提示：**
- 切到首页，展示侧边栏 8 个菜单项
- 切到关于系统的页面，展示架构图

```
┌────────────────────────────────────────────────────┐

│   6 Agent · 11 步工作流 · 19 Service               │
│   RAG引擎 · 推荐引擎 · 面试引擎 · 爬虫 · Embedding  │

│   MySQL 8 表 · Chroma 向量库 · Redis(规划中)         │
└────────────────────────────────────────────────────┘
```

**台词：**
> 整个系统分四层。

> **数据层**最下面是 MySQL 8 张核心表，和一个 Chroma 向量数据库。Chroma 存的是知识库文档的向量，用来做相似度检索。

> **往上是智能体层和服务层**，这是整个系统的核心。包括 6 个 AI 智能体、11 步的 Agentic RAG 工作流、还有 19 个 Service 文件，涵盖了从 Embedding 到 RAG 到推荐引擎到面试引擎到爬虫的所有业务逻辑。

> **再往上是 API 路由层**，用 FastAPI 写了 11 个路由模块、30 多个 REST 端点，还有一个 WebSocket 端点用来做 AI 模拟面试。

> **最上面是前端**，Vue3 + Element Plus，19 个页面。用户所有的操作都在这里完成。

> 整个项目前后端分离，后端只提供 API，前端通过 Axios 调用 REST 接口，面试对话走 WebSocket。

#### 🎬 画面：Agentic RAG 工作流流程图

  ⚪ 灰色 = 质量控制
```

**台词：**
> 这是系统最核心的流程——一键智能分析。用户上传一份简历和一个岗位 JD，点一下按钮，后台自动跑 11 个步骤。

> **前 5 步是预置步骤**：先理解用户想做什么（意图识别），把简历从 PDF 解析成结构化的 JSON，把 JD 也解析成结构化数据，规划后续步骤，然后从知识库检索相关的行业资料和岗位能力模型。

> **第 6 步是匹配分析**——这一步最关键。我把简历和 JD 交给 LLM，让它算出一个匹配度分数，同时给出优势在哪、短板在哪、有什么风险。

> **然后兵分三路**：第 7 步生成简历优化建议（告诉用户哪里要改），第 8 步生成面试题，第 9 步生成职业规划。

> **最后两步是质量保障**：第 10 步自我校验——让 AI 检查自己前面的输出有没有问题，不合格就重试。第 11 步把所有结果汇总成一份完整的报告。

> **这里有个设计亮点**：我把面试题生成和职业规划标记为"非关键步骤"。如果 LLM 调用失败，系统会跳过它们继续执行，而不是整个流程崩掉。这在用大模型做产品时非常重要——你不能让 AI 的一个小错误导致整个功能不可用。

                   │

                   │

```

**台词：**
> 第二个模块是岗位推荐。用户选一份简历，系统自动推荐适合的岗位。

> 我用了**混合排序**——两条通道并行计算：

> **向量通道**占 60% 的权重。把简历文本转成向量，去 Chroma 里搜索跟它最像的 JD。这个通道能发现文本上相似但关键词不完全匹配的岗位，比如简历写的"数据挖掘"，JD 写的"机器学习"——向量相似度能捕捉到这两者的关联。

> **规则通道**占 40%。我算了 4 个维度的规则匹配分：技能 Jaccard 相似度、经验年限匹配、薪资范围匹配、地点匹配。这些是硬指标，能保证推荐结果的实用性。

> 最后用户可以对推荐结果点赞或点踩，这些反馈会存到数据库，后续可以用于优化排序模型。

> 还有一个"岗位搜索"功能，输入关键词可以直接爬取 BOSS直聘的岗位。爬虫做了三级降级策略——首先尝试调用 API，API 不行就用 BeautifulSoup 解析 HTML，还不行就用本地模拟数据兜底。

### 模块三：AI 模拟面试（2 分钟）

#### 🎬 画面：WebSocket 面试流程图

```
┌─── 前端(Vue3) ───┐        ┌─── 后端(FastAPI) ───┐
│                   │        │                      │
│  选择简历+JD      │──REST─▶│  创建面试会话         │
│                   │        │  生成10道面试题       │
│  进入面试房间     │──WS───▶│  初始化InterviewEngine│
│                   │        │                      │
│  ◀── 面试题 ──── │◀─WS───│  发送第1题+启动计时器  │
│                   │        │                      │
│  ─── 回答 ──────▶│──WS───▶│  AI四维评估           │
│                   │        │  ↓ 低分? → 追问       │
│  ◀── 评分 ────── │◀─WS───│  ↓ 高分? → 下一题     │
│                   │        │                      │
│  (循环至结束)     │        │  10题/超时3次/主动结束│
│                   │        │                      │
│  ◀── 面试报告 ── │──REST─▶│  生成评估报告          │
└───────────────────┘        └──────────────────────┘

超时机制:
  每题30秒 → 超时跳过 → 累计3次→自动结束

评分维度:
  completeness×0.3 + accuracy×0.3 + depth×0.25 + expression×0.15

追问机制:
  overall_score < 70 且 follow_up=true → 自动追问
```

**台词：**
> 第三个模块是 AI 模拟面试。这个功能用 WebSocket 实现了真实的面试对话体验。

> **流程很简单**：用户选择简历和目标岗位，系统自动生成 10 道面试题。然后通过 WebSocket 建立连接，面试开始。

> **每轮的流程是**：AI 发一道题 → 用户输入回答 → AI 实时评估 → 给出评分和反馈 → 进入下一题或追问。

> **交互细节我做了 3 个设计**：

> **第一是超时控制**。每道题 30 秒，超时自动跳过。累计超时 3 次就结束面试。这模拟了真实面试的时间压力。

> **第二是追问机制**。如果某道题得分低于 70 分，AI 会自动追问——"刚才的回答可以再深入一些吗？能不能举一个具体的例子？"——这让面试体验更接近真人面试官。

> **第三是四维评分**。每道题从完整性、准确性、深度、表达 4 个维度打分，加权得出总分。面试结束后生成完整的评估报告，包括环形总分、各维度评分、每道题的详细评价和改进建议。

### 模块四：Query Rewrite 查询改写（1 分钟）

#### 🎬 画面：Query Rewrite 流程图

```
┌──────────────┐
│  用户原始问题  │—— "看看这个岗位适不适合我"
└──────────────┘
       │
       ▼
┌─────────────────────────────────────────┐
│           LLM 查询改写                   │
│                                          │
│  ┌──────────────────┐                    │
│  │ 技能方向 query   │ "Python FastAPI  │
│  │                   │  RAG 技能要求"    │
│  └──────────────────┘                    │
│  ┌──────────────────┐                    │
│  │ 职责方向 query   │ "后端开发 系统    │
│  │                   │  设计 工作职责"   │
│  └──────────────────┘                    │
│  ┌──────────────────┐                    │
│  │ 面试方向 query   │ "Python后端 面试  │
│  │                   │  题 高频考点"     │
│  └──────────────────┘                    │
│  ┌──────────────────┐                    │
│  │ 能力模型 query   │ "Python工程师     │
│  │                   │  能力要求"        │
│  └──────────────────┘                    │
└─────────────────────────────────────────┘
       │
       ▼
  并行检索 Chroma (4个query同时)
       │
       ▼
  合并结果 → 按chunk_id去重 → 保留最高分
       │
       ▼
  返回最终 RAG 上下文
```

**台词：**
> 这是后来加的一个增强功能——RAG 查询改写。

> 以前的 RAG 是用户问什么就搜什么。但用户的问题通常太口语化，比如"看看这个岗位适不适合我"——直接拿这个去向量检索效果很差。

> Query Rewrite 的做法是：先把用户的问题交给 LLM，让它改写成 **3 到 5 个不同维度**的检索 query。比如技能方向问"需要什么技能"，职责方向问"做什么工作"，面试方向问"会考什么"，能力模型方向问"需要什么水平"。

> 然后用这些改写后的 query **并行去 Chroma 检索**，把结果合并起来、去重、按分数排序送回给用户。

> 这样做的效果立竿见影——召回的内容从"跟问题沾边"变成了"覆盖岗位的各个方面"。

### 模块五：匹配度解释器（1 分钟）

#### 🎬 画面：6 维评分体系图

```
                   匹配度评分
                       │
        ┌──────────────┼──────────────┐
        │              │              │
   ┌────▼────┐   ┌────▼────┐   ┌────▼────┐
   │技能匹配  │   │项目经历  │   │工作经验  │
   │权重 0.35 │   │权重 0.15│   │权重 0.15│
   │Jaccard   │   │技术栈    │   │年限差    │
   │命中加分  │   │命中率    │   │          │
   └─────────┘   └─────────┘   └─────────┘
        │              │              │
   ┌────▼────┐   ┌────▼────┐   ┌────▼────┐
   │学历要求  │   │关键词    │   │加分项    │
   │权重 0.10 │   │权重 0.15│   │权重 0.10│
   │等级对比  │   │隐性要求  │   │nice_to   │
   │          │   │覆盖率    │   │_have命中 │
   └─────────┘   └─────────┘   └─────────┘
        │              │              │
        └──────────────┼──────────────┘
                       │
                       ▼
                 加权总分
                       │
                       ▼
                 扣分(缺失技能-15/经验-10/学历-5)
                       │
                       ▼
                LLM 生成自然语言解释
                       │
                       ▼
            推荐等级: 强烈/可以/谨慎/不建议
```

**台词：**
> 第五个模块是匹配度解释器。这是我在做完基础匹配功能后发现的一个问题——只给一个总分用户不知道为什么是这个分数。

> 我设计了一个**规则+LLM 的混合架构**。先用纯规则引擎算出 6 个维度的分数：技能匹配用 Jaccard 相似度加命中加分，项目经历看技术栈命中率，工作经验看年限差距，学历看等级对比，关键词看隐性要求覆盖率，加分项看 nice_to_have 的命中率。

> 每个维度有独立的算法，可解释、可调试、可复现。然后加权汇总得到总分，再减去扣分（比如缺失必备技能扣 15 分）。

> 最后才交给 LLM——**但它不参与评分，只负责写解释文案**。所以就算 LLM 挂了，分数也是准确的。

> 还有一个细节：权重不是固定的。技术岗 skill 权重 0.4，产品岗 skill 权重降到 0.25，校招学历权重提到 0.2。系统会根据岗位名称自动选择合适的权重配置。

## 第四段：数据库 & 技术选型（2 分钟）

### 🎬 画面：ER 图或 8 张表列表

**台词：**
> 数据层我用了 MySQL 8 做主存储，一共 8 张核心表。

> 这里有个设计取舍：我把**简历的解析结果**和 **JD 的解析结果**存成了 JSON 字段，而不是拆成几十个关联表。这样做的好处是灵活——LLM 解析出来的字段是不固定的，今天可能多一个"项目经历"，明天可能多一个"获奖情况"，用 JSON 就不用改表结构。

> 类似的，面试会话的**完整对话记录**、匹配度分析的**完整报告**、Agent 工作流的**中间结果**，都存成了 JSON。这在大模型产品中是个常见模式——AI 的输出结构多变，传统的关系模型反而不好用。

> 向量数据库选了 Chroma，主要是因为它零运维、pip install 即用、支持持久化。项目重启数据不丢。生产环境可以换成 Milvus 或 Pinecone。
