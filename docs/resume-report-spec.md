# 简历评估报告规范（六模块）

本文件是简历评估报告的**唯一写作规范**。`app/prompts/resume_report*.py`、
`app/services/resume_report_rubric.py`、`app/services/report_html_lint.py` 与前端报告页都按本文件口径实现，
任何一方与本文件不一致时以本文件为准，并把不一致的那一侧改过来。

它反推自一份人工确认过的成品报告（2026-09-12 版式），当时仓库里没有这份规范，只有成品。
**标了「反推待定」的数字是本仓库自己定的口径，不是成品里抄来的**，改动要在台账里点名。

---

## 1. 六个模块与顺序

模块只允许这 6 个，顺序不许变，锚点 id 不许改（导航靠 id 跳转）：

| 顺序 | 锚点 id | 导航文案 | 正文标题 | 数据来源 |
| --- | --- | --- | --- | --- |
| 1 | `m-summary` | 小结 | 不设标题，直接一段话 | 模型 + 规则求和 |
| 2 | `m-score` | 一、评分概览 | 一、评分概览（七维 100 分） | 模型给七维分，**总分与等级由规则算** |
| 3 | `m-fit` | 二、竞争分析 | 二、竞争分析 | 模型 |
| 4 | `m-resume` | 三、修改建议 | 三、修改建议 | 模型给批改点，服务端逐条校验 |
| 5 | `m-interview` | 四、面试预演 | 四、面试预演（含追问与标准答案） | 模型；总分不达标时整块换成暂缓版 |
| 6 | `m-boss` | 五、投递策略 | 五、投递策略 | **不经模型**，逐字引用 `docs/knowledge-seeds/apply_strategy/boss_zhipin_strategy.md` |

首屏结论段那一段只写四件事，中间用分隔符连着，不写"结论先行"那种补充段：
方向定位、目标等级（附判定依据）、评级（等级 + 总分）、日期。

## 2. 七维 100 分

七个维度的键名、对外标签、满分固定如下，和 = 100：

| 键 | 对外标签 | 满分 | 判分口径 |
| --- | --- | --- | --- |
| `metric_ownership` | 指标责任与达成（C）★ | 20 | 只算候选人**自己负责并达成/优化出来**的指标；团队成果与来源不明的数字不计入。看三件事：责任归属是否清楚、指标是否带口径（判定标准/样本量/标注方式）、有没有"优化前 → 优化后"。全篇只有绝对值、没有工程指标（检索 P90、单次调用成本）时压在这一档。 |
| `interview_hooks` | 面试钩子设计（E）★ | 10 | 简历里能给面试官递话的钩子数量、类型覆盖（数字/权衡/边界/踩坑四类）、在各项目上的分布、有没有会把人带进坑里的钩子。钩子停在"为什么做"、代价那一层没有数，扣分在这一档。 |
| `role_fit` | 岗位契合度（赛道定位） | 20 | 方向标签能否 5 秒判出、求职意向与优势段是否指向同一方向、该方向的词表覆盖度。技能区写了名词但项目里没有对应实践的，**只提示、不扣分**（写不写实不由这一档管）。 |
| `transferability` | 技术可迁移性 | 15 | 按 L0 会用 / L1 懂原理 / L2 能做主 给占比。多数条目要能看出选型依据与边界；跨垂类要留下一层能带走的判断，不能读成"只懂这一小块"。 |
| `project_depth` | 项目深度与真实感 | 20 | 像不像真做过：细节密度（样本量、标注规模、语料条数）、约束与代价有没有写、踩坑有没有一处、切片/解析这类参数写得够不够。 |
| `expression_structure` | 表达与结构 | 10 | 句式（动词开头、没有空泛形容词、没有无佐证的"熟练掌握"）、人称一致性、错别字与时间线连续性、**同一个数在全文前后是否一致**（数字对不上是这一档的硬伤，面试官一定会问）。 |
| `advantage_section` | 个人优势介绍 | 5 | 有独立的优势节、讲的是差异化而不是"精通 XX"、给能力配了证据、与项目一一呼应、有一条站得住的方法论标签。 |

两条硬约束：

1. **总分 = 七维之和，由服务端算，不取模型自报的 `overall_score`。** 模型自报总分只作为对照记在
   `score_overview.model_reported_total`，候选人不看它。任一维缺失或越界（非数字、布尔、小于 0、大于该维满分）
   时该维判为"未知"，总分随之为未知——**缺维度不等于 0 分**，这条沿用 `tests/test_diagnose_report_shapes.py` 已有的口径。
2. **每维的"待优化点"是一段话，不是一串通用建议。** 必须点名这份简历里的具体位置（哪个项目、哪一条职责、
   哪个数字），没有具体位置的表述视同没写。

### 等级

`A 85+`（稀缺档，七维没有明显短板）/ `B 75–84`（质量过关，可直接投）/ `C 65–74`（项目描述需要重构后再投）/
`D <65`（先补齐再谈投递）。等级由总分映射，规则计算，**不挂 AI 名头**。

评分概览结尾必须给一句"距上一档还差什么"，点名到具体位置。

## 3. 二、竞争分析

这一模块评的是**背景在同类竞争者里站哪**，与模块一的"这份简历做得好不好"不是一回事，两处的档位
可能不同，报告里要把这句话说明白。必须包含：

- 方向定位（含判定依据：附了 JD 按 JD，没附按简历关键词自动识别，并写明是哪种）；
- 竞争力档位（一句话理由，硬的基本盘 + 拖后腿的项各自点名）；
- 能打的牌（每条要能直接说出口，比如打招呼第一句）；
- 要补的短板（带时间尺度，如"1–2 天能补"）；
- 针对性建议（投递方向锁哪、不碰哪、弱项怎么绕）；
- 期望薪资：候选人填了就用他填的；没填按目标等级给一段区间参考，并写明这是参考。

**院校与年限这类只能靠时间走的项，写在短板里但要说明不必在此耗精力。**

## 4. 三、修改建议（Word 审阅式批改稿）

- **主体是候选人的原简历**：按原简历的章节与项目顺序铺开，未改动的句子原样保留、不加标记，
  不得重排、合并、删节章节。
- **原简历全部内容都要出现**：基本信息 / 个人优势 / 技能清单 / **每一个项目**（第 1 个、第 2 个……
  一直到最后一个）/ 工作经历 / 教育背景，一段都不许省。
  **严禁"同上 / 以此类推 / 其余项目照此 / 此处省略"这类省略写法**——那样候选人拿到的是半份稿子。
  机检（`report_html_lint.py`）命中即报错。
- **改动分两档，两档都要写出来**：
  - `key`（必改）：改完能上到 80 分线的关键项 → 编号与批注标"关键"；
  - `normal`（建议改）：责任颗粒度、约束/代价/口径补齐、表述呼应等提升项 → 照常编号 + 批注，但不标"关键"。
  - 只出 key、把 normal 略过视为未完成。**纯润色是第三档，不写。**
- **两套记号不许混**：档位说的是改动优先级，项目编号（项目 1 / 项目 2）说的是第几个项目。
  成稿里档位只以"关键"徽标体现，**不写 P0/P1 字样**；项目一律写成 `项目 N · 项目名`。
- 要动的地方才标：`del` 写"建议改掉的原话"，`ins` 写"建议改成的内容"，紧跟编号；
  右栏每条批注对应一处改动，**编号与正文严格一一对应、不多不少**；批注先写"这么改解决什么
  （面试官会怎么追问 / 现在卡在哪）"，再给动作。
- 顶部计数"共 n 处改动，其中 m 处是关键项"**必须与正文实际数量一致**，机检会核对。
- **零改动/极少改动怎么办（不许为过机检硬凑）**：简历本身达标时就老实铺原文，只在真值得动的地方标几笔。
  计数三档写法：① 有关键必改项 →"共 n 处改动，其中 m 处是关键项"；② 只有可选优化 →"共 n 处可选优化，
  没有必改项"；③ 一处都不必改 →"这一版可以原样用，无需改动"。第 ②③ 种情况下 `del`/`ins` 可以为空，
  右栏放一条**不带编号**的批注说明理由。
- **服务端校验（`resume_redline_service.validate_redline_edits`）**：`del` 必须逐字命中所在块文本的子串，
  命中不了就整条拒掉并记原因；一条 `del` 在同块内命中多次也拒（位置不确定）；编号不连续、批注与编号
  数量不等、声明数与实际数不等同样拒。拒因对内可查，不上候选人的屏。

## 5. 事实边界与写法红线

**这些是硬约束，机检逐条扫：**

- **不编数字。** 没实测过的写 `【待补：按 X 路径跑一遍得到实测值】`，不许给一个看起来合理的数。
  `ins` 里出现原文没有的数字，只有包在 `【待补：…】` 里才合法。
- **严禁把"参与/协助"写成"主导/负责"**，只做职责颗粒度细化。
- **成稿措辞不得出现内部机制字眼**，也不解释给分机制。禁词表（`report_html_lint.py` 用同一张表）：
  兜底、总分兜底、不低于 65、严格制、软下限、门禁、可面试水位、硬条件、双轴、收敛、档内区分项。
- **全文口径自洽**：分数、等级、薪资数字、面试题状态前后一致，不得出现两种说法。
- **示例内容必须全部替换**：技能那份模板自己的示例值（`李明`、`81/100`、`企业知识库问答助手`）
  不得出现在任何一份生成报告里，机检第 7 项扫的就是这三个。
  **反推所用的那份真人成品没有进仓**：它的姓名、手机号、邮箱在进 `tests/fixtures/` 时被换成
  `示例候选人 / 13600000001 / probe@example.com` 三个假 token，结构一字未动。
  mock 夹具除外——mock 载荷必须带 `（mock）` 前缀，机检把带 `（mock）` 的文件判为夹具。
  **一个刻意的例外（D231）**：批改稿的 `ins` 不带这个前缀，因为它是会被"采纳"原样写回简历正文的那一位，
  带标记的简历文本没人能用；标记落在同一条批注的 `note` 上。由
  `backend/tests/test_resume_report_mock_stages.py::test_mock_payloads_are_marked_as_fixtures` 钉住这一条例外。
- AI 降级对候选人静默：模型不可用时报告不出现"AI 挂了"这类话，走 §2 的"未知"口径。

## 6. 四、面试预演

- 每题四件套：题干、**【标准答案】第一人称口述稿**（照着能念的一段，不是要点列表）、
  **【追问 1/2/3】**每条带类型标签、**状态**。
- 追问类型只允许：为什么、权衡/代价、边界、对比、数据、踩坑、如果……（机检按这张白名单扫标签）。
- 状态两态：`✅ 可答` / `⚠️ 需补强（缺：xxx、xxx）`。"需补强"必须点名缺的是哪个数、哪段口径。
- 标题下要给题型分布：基础概念 / 项目深挖 / 对比权衡 / 踩坑与边界 / 场景设计 各几题，
  以及按项目分组各几题、另加几道通用题。**分布数由服务端数出来，不取模型自报**（模型自报的
  `total_questions` 历来和实际题数对不上）。
- **总分低于 65 时整块换成"暂缓生成"版**：这一段只说"先把三处必改项补上、跑完【待补】的数，
  这一节再做价值更大"，不出题。对外文案不许出现"门禁""阈值"这些字眼（§5 禁词表）。
  65 这个数成品里没有（它只写了 A/B/C 三档的文字），是本仓库按 C 档下界自定的，
  **2026-10-13 由 zzh200215 确认取 65**；要改只改 `resume_report_rubric.INTERVIEW_MIN_TOTAL` 一处。

## 7. 五、投递策略

逐字引用 `docs/knowledge-seeds/apply_strategy/boss_zhipin_strategy.md` 的第一至五节，**一次 LLM 调用都不过**：
这一节的内容不依赖这份简历，让模型复述只会引入编造风险，也白花一次调用。
简历个性化只落在两处——在线简历的一句话标签取"个人优势"的第一句原文，打招呼话术里的项目亮点取竞争分析那张
能打的牌。这两处由 `resume_report_service.build_personalization` 算在**数据层**
（`report.personalization = {one_line_label, opener}`），HTML 渲染器与应用内那一页都只读它、不各自重算：
同一句话有两个出处的话，两个形态迟早长得不一样。两处都是引用，不新写句子、不新增数字。
被引用的候选人原文在 HTML 里带 `class="quoted-resume"`，机检的机制字眼扫描对它豁免（与 `.paper` 同一条理由）。

## 8. 交付形态与技术约束

两个形态，同源同一份结构化数据：

1. **应用内一页报告**（`frontend/src/features/resume/views/ResumeReport.vue`）：六模块顺序、锚点、
   左右栏批注、切净稿、复制净稿与打印样式都按本文件。
2. **可下载的独立 HTML**：文件名 `简历评估报告_{姓名}.html`，**纯内联 CSS/JS，不引用任何外部资源
   （无 CDN、无字体、无图片）**，双击即开、离线可用，浅色主题、可打印（打印时自动隐藏导航与回顶部按钮）。
   渲染器 `app/services/resume_report_html.py` 是唯一产出方；前端不提供第二套 HTML 拼装逻辑。

## 9. 机检清单（`app/services/report_html_lint.py`）

交付前逐条判，任何一条不过就报错。移植自成品注释里那份 `report_html_lint.py`，共 7 条：

1. 导航项与模块锚点一一对应（六个、顺序一致、没有指向不存在 id 的项）。
2. 必需模块齐全（六个 id 全在且非空）。
3. 批改稿编号与右栏批注一一对应，不多不少、编号连续。
4. `.rvstat` 声明的"共 n 处 / 其中 m 处关键项"与正文实际计数一致。
5. 禁省略写法：`同上`、`以此类推`、`其余项目照此`、`此处省略`、`P2 … Pn`。
6. 禁内部机制字眼（§5 那张禁词表）。
7. 禁未替换的示例内容（§5 那份示例姓名/数字表）。

反向证据由 `tests/test_report_html_lint.py` 提供：一条一份变异，每发只红它自己那条。
