# 组合分析（多项目）写作规范

这一族量的既不是整份简历，也不是单个项目，而是**被选中的几个项目叠在一起**。
三把尺各量一件事，任何一处混用都会让两份交付物对同一句话给出两个数。

反推来源：人工确认过的成品《总分析.html》（三项目组合，可见正文 13,948 字）。
**这份成品是人为一个人写的三份项目文本整理的，不是本仓库跑出来的**；
下面凡是"反推待定"的都是本仓库自定的口径，成品里没有那个数，改动要在台账里点名。

---

## 1. 四个模块与顺序

| 节 | 锚点 | 里面有什么 | 过不过模型 |
| --- | --- | --- | --- |
| 一、组合档案 | `c-profile` | 1.1 六维评分卡 / 1.2 项目横向对比 / 1.3 能力覆盖矩阵 / 1.4 整体风险提示 / 1.5 选中项目原文 | 前两发问，1.5 一个字不问 |
| 二、组合图解 | `c-diagrams` | 2.1 覆盖矩阵（画成格子）/ 2.2 叙事主线 / 2.3 技术栈复用与差异 / 2.4 跨项目面试时序 | 问一发；2.1 与 2.3 的两栏不问 |
| 三、使用建议 | `c-advice` | 3.1 排列建议 / 3.2 被问怎么答 / 3.3 补强路径 / 3.4 引用红线 | 问一发 |
| 四、跨项目面试 | `c-questions` | 12 题，每题标准答案 + 两轮追问 | **按按钮才问的那一发** |

节名与锚点的唯一权威是 `portfolio_report_html_lint.SECTIONS`，渲染器 import 它；
少画一节会被导航那条拦住。第四节没生成时整块缺席（导航里也不留那一栏），
页脚写一句"这一份下载时第四节还没生成"。

**2~N 泛化**：项目数由勾选决定（至少两个），表格列数、叙事主线的阶段数、
覆盖矩阵的行数都跟着它走。参考件正好是三个，但锁死三个会让库里两份项目的简历用不了这一功能。

## 2. 第三把尺：组合六维（24/24/19/14/14/5）

`app/services/portfolio_report_rubric.py` 是唯一权威。满分分配与单项目那把**相同**
（参考件 1.1 那张表就是这套数），维度名与判据换成组合口径：D2 问的是"换皮没有"、
D5 只问跨项目那一层。**同一份简历那把七维尺（评级用字母）与单项目那把六维尺都不参与这里。**

### 三处故意的不对齐

1. **档位区间自切**（反推待定）。唯一样本：参考件组合 94 分写的是"优秀"，
   而单项目那把尺 90 以上叫"标杆级"。照抄那套区间会让 94 变成标杆级、与成品矛盾，
   所以组合按 标杆级 95–100 / 优秀 88–94 / 良好 75–87 / 需重组 60–74 / 暂不可投 0–59 切。
   代价是"优秀"这个词在两把尺里不是同一个分数带——**报告在合计下面那一行明写这一句**，不偷偷复用。
2. **难度档位不新造、也不认 "L5+"**。参考件表头写的是 `L5+`，树里没有加号这一档；
   白名单沿用 L1–L5，模型提名 L5+ 会被 `is_known_difficulty` 拒掉并记一条对内差异。
3. **1.3 的「组合覆盖」那一列由格子推**，不接受模型写的词，所以措辞与参考件不同：
   参考件那一格写"强（金融最完整）"这种带编辑色彩的话，机器推不出"最完整"，
   推出来的是"强（1/3 项重点覆盖）"。判据：全项目重点覆盖=极强；有重点覆盖=强；
   只有部分覆盖=中；一格都没有=未覆盖。

### D6 位次与叙事（服务端算，模型不给分）

起始位次定基本盘（沿用单项目那把的 5/3/1 系数），跨多位扣 1 分，最低 1 分——
`span_score([0,1,2]) = 4` 正好复现参考件那一格的 4 分与合计 94。落档那一格写的是
**占了第几位到哪几位**（"第 1~3 位"），不是这一维的得分；拿得分当位次会打成"第 4 位"，
D236 的活页读数在单项目那一族抓到过同一形状的错，这一族一开始就钉了两棵树。

## 3. 表头那一排：有一个数是可以整格留空的

`项目数` / `组合评分` / `组合难度` / **`单项目均分`**。前三格与另两族同一条纪律（全部服务端算）。

第四格按他点的口径："有就复用，没有留空"——它取的是**已经跑过且给得出分**的单项目分析
（`peer_project_totals` 读 `project_report_job` 里每个项目最新那一发**完成的** report 行；
命中红线的那份没有分，不算进去）。一份都没跑过时那一格写
`还没跑过单项目分析，这一格空着`，不是 0、不是"未评分"、更不是模型自报的一个数。
只跑过一部分时写 `88（只有 1/3 个跑过单项目分析）`——**缺了几份要一起上屏**，
一个少算了一份的平均数比"没算出来"更坏，它看起来像个真数。

## 4. 红线（一票否决）

判法两档与另两族同一条口径：`code` = 服务端自己算，`model` = 模型只能提名，
且证据必须**逐字落在被选项目原文的并集**里，命不中整条作废。

| 键 | 判法 | 够不够出局 |
| --- | --- | --- |
| `duplicate_projects` 同一个项目换名字写了两遍 | code | **够**：折叠掉空白与标点后逐字相同 |
| （近似雷同，折叠后相似度 ≥ 0.85） | code | **不够**，只出证据与计数 |
| `others_work_combo` 整组不是本人参与却都写成自己的 | model | 够（要逐字证据） |
| `no_growth_line` 一条路走了三遍、给不出任何独有决策 | model | 够（要逐字证据） |
| `unanswerable_combo` 组合层一问就穿 | model | 够（要逐字证据） |

"至少两个项目"**不是红线**——那是请求不成立，接口层直接拒（一条永远不会在合法输入上
命中的规则不配当门）。近似雷同不判出局的理由与 D236 那条同形：同一家公司两个项目
共用一栈是常态，按它拦会把合法组合判死。**阈值 0.85 是反推待定**：2026-10-15 在一份
真三项目简历上量到的相似度是 0.007 / 0.016 / 0.029，离阈值很远，`duplicate_pairs` 为空。
样本只有一个，要改这个数得先量更多真简历。

命中红线的后果：不给总分也不给等级（**库里那一列也不留分**，与文档那句"不作数"必须一致，
否则列表读列、详情读文档会打架），第四节按口径不出题、接口层拒绝续跑并给人话说明。

## 5. 二、组合图解里"不问模型"的那两处

* **2.1 就是 1.3 那张表换一种画法**，权威只有一处，不再问第二次；
* **2.3 的共用栈 / 差异栈两栏由服务端从每个项目的技术栈清单求交集算**
  （`stack_reuse`）：共用 = 出现在 ≥2 个项目里，差异 = 只出现在 1 个里；
  并列写法（"Chroma / Milvus"）拆开各自算。比对用折叠形（大小写、连字符、空格不算差异），
  **上屏用原文里那个写法**——把 FastAPI 画成 fastapi 会让人以为是另一只组件。
  模型自报的 `shared_stack` 只是提名：不在交集里的一律丢弃并记对内。
  这两栏分别回答"这套选型稳不稳"和"是不是照搬"，正是回答同质化质疑的两层，
  所以宁可只列真在清单里出现过的。
* 2.2 的阶段数必须等于项目数、每个项目恰好出现一次；2.4 的五轮键写死在白名单里，
  第三轮与第四轮标"胜负手"（这一句直接来自成品原文）。

## 6. 三、使用建议：那一格排列由服务端渲染

3.1 每一行模型只给一个 `project_indices` 排列，服务端校验它是被选项目的**合法全排列**，
再渲染成 `PJ-01 → PJ-03 → PJ-02`；不是全排列的行整行丢弃。这一格是最容易被写成
"顺便再夸一个简历上没有的项目"的地方，所以名字不由模型拼。
3.3 的"补齐后预计"必须点名组合六维里的某一维（D2 / "区分度" 都行），不点名的那句只是好话。

与单项目那一族**不同**的一处：组合的使用建议没有"必练题/高危题"那两行（成品 3.x 里没有），
所以第四节生成完不回填第三节，题号只出现在第四节自己那一段。

## 7. 事实边界与措辞

四条界的写法与另两族同源，这里只列这一族特有的：
1. **失败粒度跟着缺陷粒度走**（D236 那轮在真简历上学的）：横向对比里一个数字只撤**那一格**
   （上屏写"这一格的说法里有一个不在项目原文里的数字，已撤下"），叙事主线里一条要点只撤**那一条**；
   整行都被撤下才丢那一行，主线/时序两块都不合格才让整节缺席。
2. 逐字摘录（1.5）一个字不过模型；红线证据按被选项目原文的并集核。
3. 编造数字按字符串叶子查，服务端自分配的编号（`no`、`project_index`、`expected`、`level`）不参与。
4. 候选人视图里不许出现内部键（拒因、证据、模型出处、共用栈明细）。

prompt 注入边界：`projects_block` / `stack_block` / `project_excerpt` / `peer_projects_json`
都登记进 `prompts/rendering.py` 的 `_UNTRUSTED_FIELD_TAGS`，包成数据标签而不是指令。
这一条本轮补齐到了**单项目那一族**（那两支持以前是裸拼项目正文的）。

## 8. 交付形态

* **作业行**：`portfolio_report_job`（迁移 `20261014_0032`）。键是 `combo_key`
  （选中项目的规范化序号串，与勾选顺序无关），不是 `project_index`；
  `stage` 两个值（report / questions），子行指回父行，文档只存父行那一份。
* **路由**四支：POST `/{resume_id}/portfolio-report-jobs`、GET `/portfolio-report-jobs/{job_id}`、
  POST `/…/{job_id}/questions`、GET `/…/{job_id}/report.html`。
  不传 `project_indices` 就是"这份简历里写出来的全部项目"。
* **两种渲染**：后端自包含 HTML（离线双击可开、零外部资源）与应用内 `PortfolioReport.vue`，
  读的是同一份装配出来的文档。两棵树的形状由
  `frontend/tests/fixtures/portfolioReportShape.json` 钉住（后端真输出导出，
  反向守卫 `tests/test_portfolio_mock_shape_fixture.py` 盯着它不过期）。
* **两张随项目数变宽的表（1.2 横向对比、1.3 与 2.1 覆盖矩阵）钉了地板宽**：
  外层 `.tscroll{overflow-x:auto}`，表本身 `min-width = 96 + 86 × N (+100 尾列)`，
  三个常数在 `portfolio_report_rubric.wide_table_min_px()` 一处权威，前端抄成同名 JS 常量
  （`noteAbsentPhrase.test.mjs` 那条比这三个数）。**为什么要有这一条**：2026-10-15 在 307px 视口上量的，
  没套容器时整张表按可视宽硬压，矩阵格子压到 **36px**、一个能力名换 6 行，
  四个项目起整页顶出横向滚动条（N=4 溢出 24px、N=5 **86px**）；
  套上地板宽（N=2/3/4/5 → 268/354/440/526，矩阵各 +100）后同一档实测**页面溢出全 0**，
  矩阵格子回到 86px、最坏单元格 6 行 → 3 行，对比表最窄格 35px → 41px、最坏 10 行 → 7 行，
  而 1080 / 900 两档的表宽与改前逐字相同（991 / 811）、滚动容器 `scrollWidth-clientWidth = 0`——
  宽屏那一份没被这笔改动碰到。
* **1.1 那张六维评分卡照同一配方，吃的是一个固定宽 `SCORECARD_MIN_PX = 470`**：它五列固定、
  不随 N 长，但 307px 视口实测"主要扣分理由"那一格被压到 **63px、一句话排 15 行**。
  470 这个数取自这张表自己在 560px 那一档的实测分配（85/41/46/58/240），不是拟的——
  改后按同一把尺重跑：560 档复现出 85/41/46/58/240、400 与 307 档表宽钉在 470、
  理由格 63 → **239px**、最坏单元格 **15 行 → 4 行**、整页溢出 0。
  **代价写明白**：这一张在 307px 上要在容器里横滑 252px（400px 上 159px），换掉的是"一句话排十五行"。
  1080 档逐字未变（991、列宽 184/53/53/88/612）。
* **打印那一档把地板宽放开**：`@media print` 里加 `.tscroll{overflow-x:visible}` 与
  `.tscroll table{min-width:0!important}`。理由是算术：A4 竖版去掉页边距可用宽实测 673px，
  N=5 的矩阵地板宽 626px 还塞得下，**N=6 起是 712px 就会被切**——打印时改回"按页宽压"而不是"切掉列"。

## 9. 机检清单（`app/services/portfolio_report_html_lint.py`）

十六条，每一条对应一个"这一份会让人误信"的具体形状：导航与四大节一一对、
每一节非空的定义逐节点名、合计等于六维相加、空栏标记那句话的计数、
出局形态（有红线栏、无题目正文；不命中时不许挂红线栏）、
摘录块数等于项目数且逐行在原文里、机制字眼与省略写法、markdown 记号漏出、
**表头两格（项目数 / 单项目均分）等于服务端那一个**、
横向对比行列齐且不留空、**覆盖那一列等于按画出来的格子推出来的那一句（两条腿各判一侧）**、
**那三张压不得的表（评分卡 + 横向对比 + 两处矩阵）都套着滚动容器、且带的地板宽等于服务端那一个**、
叙事主线段数等于项目数且不重不漏、时序五轮齐、共用栈一栏不许漏掉服务端算出的组件、
题数声明与实际一致且每题两轮追问且标签合法、零外部资源。

## 10. 这一族还没做的

* 组合分析目前不看整份简历那份七维报告的结论，也不把它的分数引过来；
  两份都在的时候要不要互相指认（例如组合的 D2 用整份报告的项目分布做佐证），没有依据，先不做。
* **形状与观感都量过了，量出过一个真缺陷**（2026-10-15，临时库 + 五项目合成简历 + 真浏览器）。
  形状那条是门：后端 `test_泛化到五个项目时列数跟着长且机检仍全过`（N=2/3/4/5 各渲一份过机检，
  列数、段数、`PJ-0N`、排列箭头数全部从数据推），前端另有 `portfolioReportShape4.json`
  那一组（四个项目的**真后端输出**，同一支 collector 一次跑出，反向守卫逐字比过）。
  观感那条量出来是坏的：页面这一棵树的 1.3 曾给列头与格子挂了 `.n`（`white-space: nowrap`），
  五个项目时它的最小内容宽度被五个「项目 N · 一长串项目名」钉死在 **897px**——
  容器 900 时压出卡片 20px、780 时 140px、**640 时 280px**，整页被顶出横向滚动条。
  撤掉那个类 + 外套一层 `overflow-x:auto` 后同一组宽度实测 954 / 854 / 734 / 594、
  卡片溢出全 0、最窄列 75–125px（表头改可换行）。**下载那份当时就没这问题**
  （895 / 795 / 675 / 535，`body.scrollWidth` 与可视宽逐档相等），两处各自量过才分开写。
* **≤400px 与打印预览这一档也量完了，量出来是坏的、已修**（2026-10-15，同一族下载件 N=2/3/4/5
  各渲一份，内嵌标签页视口这次自己落在 307px）。上面那条"下载那份当时就没这问题"只对**宽屏**成立：
  窄到 307 时下载件里那两张随项目数变的表把整页顶出 24px（N=4）／**86px**（N=5）横向滚动条，
  矩阵格子压到 36px。修法与改后读数都记在 §8，判据记在 §9；打印那一侧从 CSSOM 逐条取出
  `@media print` 那 6 条规则注入后测，794 与 718 两档页面溢出全 0、最宽那张表 min-content 349 < 可用 673。
  **这轮仍然没量的两条**：① 应用内那一棵树的**像素**——jsdom 不排版，前端只钉了"套没套容器 + 内联宽"
  两条结构断言，像素那一份是从下载件同一族 CSS 上读的，要收这条得在能改视口的地方再读一遍；
  ② 真机触屏（惯性滑动、`-webkit-overflow-scrolling`）与打印对话框里实际分页断点。
  （原来第三条"1.1 那张表没进判据"已经按同一配方收掉了，读数与代价记在 §8。）
* `NEAR_COPY_THRESHOLD` 只有一份真简历的读数（见 §4）。
