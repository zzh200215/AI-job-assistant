# AI 模拟面试 — WebSocket 消息协议

## 连接地址

```
wss://<host>/ws/interview/{session_id}
```

凭据**只能通过 WebSocket 子协议传**，不能放在 URL 里：

```js
// 浏览器侧（frontend/src/api/interview.js 就是这么写的）
new WebSocket(url, ["jwt", token])
```

- `session_id`：面试会话 ID（通过 REST API 创建）
- `token`：JWT 认证 Token（与 REST API 共用），放在子协议第二项
- 服务端会回 `Sec-WebSocket-Protocol: jwt`。`?token=` 这种写法**自 E16 起直接 4001 拒绝**——
  长期 JWT 落进 nginx/网关访问日志与浏览器历史，正是这条通道要防的事（改前它仍被接受，已实测）。
  命令行调试时需要能发子协议头的工具，例如 `websocat --sec-proto "jwt,$TOKEN" wss://host/ws/interview/7`
  （本机未装 websocat，这条命令未实测）。

## 连接生命周期

```
客户端                           服务端
  |                                |
  |---- WS Connect (带 token) ---->|  1. 认证 + 校验会话归属
  |<-- Accept / Close(4001) -------|  2. 建立连接 / 拒绝
  |<-- {"type":"question", ...} ---|  3. 自动开始，发送第一题
  |---- {"type":"answer",...} ---->|  4. 用户回答
  |<-- {"type":"system",...} ------|  5. 回答已持久化，评分转入后台
  |<-- {"type":"question", ...} ---|  6. 下一题 / 追问（不等待评分）
  |---- GET /sessions/{id}/evaluations ->|  7. 轮询已完成评分与证据
  |          ...                    |
  |<-- {"type":"end", ...} -------|  7. 面试结束
  |<-- Close(1000) ---------------|  8. 服务端断开
```

## 消息类型总览

| 方向 | type | 说明 | 触发时机 |
|------|------|------|---------|
| C→S | `answer` | 用户回答当前问题 | 用户输入后 |
| C→S | `skip` | 跳过当前题 | 用户点击跳过 |
| C→S | `end` | 用户主动结束面试 | 用户点击结束 |
| C→S | `ping` | 心跳检测 | 每 15 秒 |
| S→C | `question` | AI 面试官提问 | 面试开始 / 每轮开始 |
| REST | `GET /sessions/{id}/evaluations` | 异步评分、证据与记忆状态 | 面试进行中轮询 |
| S→C | `evaluation` | AI 评分反馈 | 后台评分完成后回流 |
| S→C | `system` | 超时/系统提示 | 超时 / 状态变化 |
| S→C | `end` | 面试结束（含报告） | 面试完成 |
| S→C | `pong` | 心跳回应 | 收到 ping |
| S→C | `error` | 错误信息 | 任何异常 |

## 消息格式详情

### 1. 客户端 → 服务端

#### `answer` — 用户回答

```json
{
  "type": "answer",
  "content": "FastAPI 的依赖注入通过 Depends 函数实现，当路由函数声明了 Depends(...) 参数时，FastAPI 会在调用前解析依赖树..."
}
```

#### `skip` — 跳过当前题

```json
{
  "type": "skip",
  "content": ""
}
```

#### `end` — 主动结束面试

```json
{
  "type": "end",
  "content": ""
}
```

#### `ping` — 心跳

```json
{
  "type": "ping",
  "content": ""
}
```

### 2. 服务端 → 客户端

#### `question` — AI 面试官提问

```json
{
  "type": "question",
  "content": "请介绍一下 FastAPI 的依赖注入机制是如何工作的？",
  "metadata": {
    "round": 1,
    "total": 10,
    "category": "技术基础",
    "timeout_seconds": 120,
    "question_id": 3,
    "is_follow_up": false,
    "turn_id": "q-1"
  }
}
```

| metadata 字段 | 类型 | 说明 |
|:---|:---|:---|
| `round` | int | 当前题号（1-based） |
| `total` | int | 总题数 |
| `category` | string | 题目分类: 技术基础 / 项目经验 / 通用HR / 情景场景 |
| `timeout_seconds` | int | **这一题的作答预算**（D238 P1.2）。服务端超时与前端倒计时共用这一个数 |
| `question_id` | int | 题目唯一 ID |
| `is_follow_up` | bool | 是否为追问（默认 false） |
| `turn_id` | string | 该回答与评分证据的稳定关联 ID |
| `decision` | object | **可选**（D239 P3.1）。动态面试官决策器为这一题出的决策：`{"action": "deepen\|advance", "source": "llm\|heuristic\|starter", "degraded": bool?}` |

**关于 `decision` 这一格**（先把形状钉在协议里，再说它什么时候出现）：

- **老客户端必须能忽略它。** 上面六个键（`round`/`total`/`category`/`timeout_seconds`/`question_id`/`turn_id`）
  一个都不许改名或消失——这条有测试盯着（`backend/tests/test_interview_decision_graph_guardrails.py`），
  新增只许是可选键。
- `action` 是"这一题是深挖还是推进"；`source` 说这一题从哪一级来的：候选池/引擎原来那份题目列表
  （`starter`）、决策器的启发式（`heuristic`）、还是 LLM 现场组织（`llm`）。
- `degraded` **只在决策器降级时出现**（LLM 决策炸 ⇒ 落启发式）。它对候选人是静默的：屏幕上不会
  出现"面试官降级了"这种话，这个键只是给对内可查与告警用的（`AI 降级对候选人静默` 那条产品决策）。
- **当前发出状态**（2026-10-18 更新）：**已经在发了**。引擎接线那一格落地（开关 `INTERVIEW_USE_DECIDER`，
  默认开），只有**追问那一条 question 消息**带 `decision`，正常按题序出的那条不带这个键；开关关掉 ⇒
  一条追问都不出，回到今天那条链（含 I3 那套模板追问——两套不并存，模板只在开关关掉时启用）。
  已量到的边界：① 决策器目前只走**启发式**那一档（`chat=None`），LLM 现场组织追问还没接进来；
  ② "同一轮出现第二条 question 消息"在断线重连与逐题评分链上的行为**已验证**（2026-10-19）：
  追问未答时重连把同一条再推一次；追问已答时不重推、接着推下一道主题；追问的答案在评分表里
  是独立一行（`turn_id = q-N-followup`），不会覆盖主题那一行。详见 `简历与面试优化.md` §4 P3 那节。

**`timeout_seconds` 的取值与兜底**（客户端必须实现兜底那一条）：

| 题型 | 默认预算 |
|:---|:---|
| `basic`（通用 / HR） | 45 秒 |
| `tech`（技术基础） | 120 秒 |
| `scenario`（情景场景） | 90 秒 |
| `project`（项目经验） | 120 秒 |

- 这张表可以被平台级配置覆盖（`interview_question_bank.timeout_seconds`，`tenant_id IS NULL` 那一档），
  回落顺序是 **平台配置 → 上表内置默认 → 认不出题型时 45 秒**。
- **认不出题型时发的是 45 秒，不是这次改动之前的 30 秒。** 30 秒就是"系统设计题根本答不完"那条硬伤的
  来源，所以它不作为任何兜底值继续存在。
- **老会话落库的 `question` 消息里没有这个字段**，客户端取不到时必须兜底到 **45**，
  不许自己抄一个 30 回去：`stores/interview.js` 里那个常量同时是三处倒计时的起点**和**进度条的分母，
  抄回去的话 120 秒的一题会在 4 秒时显示成"时间到"，而服务端还在等你。
- 值为 0、负数或非整数（手改过 JSON 列的历史行）一律按 45 处理——睡 0 秒等于一出题就判超时。
- 超时判定以**服务端**为准：这条消息只是把同一个数告诉客户端用于显示，前端倒计时归零不等于超时。

#### `evaluation` — AI 评分反馈

```json
{
  "type": "evaluation",
  "content": "{\"score\": 85, \"feedback\": \"回答全面且深入，对源码理解到位\"}",
  "metadata": {
    "round": 1,
    "score": 85,
    "completeness": 90,
    "accuracy": 85,
    "depth": 80,
    "expression": 85,
    "turn_id": "q-1",
    "async": true,
    "evidence": {"source": "answer_evaluation_agent", "answer_excerpt": "..."}
  }
}
```

| metadata 字段 | 类型 | 范围 | 说明 |
|:---|:---|:---|:---|
| `round` | int | 1- | 题号 |
| `score` | int | 0-100 | 总分 |
| `completeness` | int | 0-100 | 完整性评分 |
| `accuracy` | int | 0-100 | 准确性评分 |
| `depth` | int | 0-100 | 深度评分 |
| `expression` | int | 0-100 | 表达评分 |
| `turn_id` | string | - | 关联提问、回答与持久化评分记录 |
| `evidence` | object | - | 评分时使用的回答摘要和维度证据 |

### 异步评分查询

```text
GET /api/interview/sessions/{session_id}/evaluations
```

返回 `items`（逐题 `pending/running/completed` 状态）、`evaluation_status` 和 `memory_snapshot`。该接口只允许面试会话所属用户访问。最终报告若仍处于 `processing`，前端应继续刷新，直到后台评分全部完成。

**评分等级：**
- 85-100: 优秀 (绿色)
- 70-84: 良好 (蓝色)
- 55-69: 一般 (橙色)
- 0-54: 待提升 (红色)

**总分加权公式：**
```
overall_score = completeness × 0.3 + accuracy × 0.3 + depth × 0.25 + expression × 0.15
```

## 关闭码说明

| Code | 含义 |
|:---|:---|
| 1000 | 正常结束（面试完成） |
| 4000 | 面试已结束 |
| 4001 | 认证失败（Token 无效／缺凭据／凭据放在 URL 查询串） |
| 4003 | 无权访问 |
| 4004 | 会话不存在 |
| 4005 | 并发面试已达本进程上限（`WS_MAX_LIVE_INTERVIEWS`，默认 12） |

## 超时机制

- 每道题的超时时间为 **30 秒**（从题目发送开始计时）
- 超时后，服务端发送 `{"type": "system", "content": "⏰ 第X题回答超时（Y/3次）"}`
- 自动跳过当前题，进入下一题（`question` 消息）
- 累计超时 **3 次** → 自动结束面试（`end` 消息）

## 面试结束条件

满足任一条件即结束：
1. 所有题目完成
2. 用户发送 `{"type": "end"}`
3. 累计超时 3 次
